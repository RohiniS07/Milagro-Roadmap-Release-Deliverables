Payment flows move only after the low-risk read path is proven and receive stricter parity and QA controls.
02

Design Principles

DECIDED
6 fixed principles

Six principles are fixed and shape everything below.

01 · SCOPE
One service, not many
A single deployable microservice now — not a fleet. Multiple services stay a future option, not this milestone.
02 · STRUCTURE
Built to split later
Organised by module so any part can be lifted into its own service later with minimal effort, if the need arises.
03 · SHARING
Shared logic in one place
Common code lives in shared workspace libraries, never copied — so fixes land once.
04 · CONTRACT
Industry-standard API naming
Clean, REST-style names using standard POS vocabulary (order, check, tender, refund), replacing legacy naming.
05 · DATA
Modern data layer (Prisma)
A typed, safer database layer — on the existing shared database, so no data migration and no data risk.
06 · QUALITY
Small, maintainable files
A hard file-size limit (≤500 LOC) enforced automatically, keeping the code readable and reviewable long-term.

Migration Contract

CONTRACT
5 rules · non-negotiable

Every endpoint follows these compatibility rules unless an explicitly approved follow-up says otherwise.

01 · CONTRACT
Preserve requests & responses
Keep query parameters, request bodies, status codes, response fields, and the LoopBack-compatible envelope unchanged during migration.
02 · CLIENT
Endpoint swap by default
Android and web clients change only the endpoint URL. Existing models and business logic remain unchanged unless separately reviewed and approved.
03 · COEXISTENCE
Keep legacy routes live
The monolith route and the new /api/v5/pos/_ route operate in parallel until every known consumer has migrated.
04 · CLEANUP
Separate optimization work
Field cleanup, payload reduction, REST-model redesign, and response optimization are opt-in follow-ups — not bundled into the service move.
05 · MONEY
Stricter payment parity
Payment requests and responses remain byte-identical, with no idempotency or client-flow changes introduced as part of migration.
08

Rollout Strategy — One API at a Time

ROLLOUT

Every API migrates through the same safe, reversible sequence. Old and new run in parallel until the field has drained onto the new app version.

1 · BACKEND
Deploy new, keep legacy
Ship the new /api/v5/pos/… endpoint on the microservice. The legacy /api/PosTransactions/… stays live on the monolith — both operational.
2 · ANDROID
New version opts in
A new app version calls the new endpoint; existing installed versions keep using the legacy endpoint. No forced update.
3 · COEXIST
Run both until adoption
Both paths serve production traffic until new-version adoption reaches the agreed threshold (to be set by Product).
4 · DEPRECATE
Retire legacy
Once old app versions are effectively unused, deprecate then remove the legacy endpoint from the monolith.
↺ · ROLLBACK
One-line revert
Revert the nginx route → traffic falls straight back to the monolith in seconds. New app versions can be toggled off via remote config.
✓ · VALIDATE
Success criteria
Response parity (golden fixtures), error-rate & latency within SLO, no rise in support tickets — per API before moving to the next.
Why this is safe. Because the DB is shared and the contract is byte-identical, the new and legacy endpoints operate on the same rows with the same behaviour — so parallel-running and rollback carry no data risk. Releasing one API at a time keeps every change independently verifiable and reversible.
09

What Keeps This Safe — and What Could Slow It

RISK
✅ The scariest part isn't moving
Card charging happens on the payment terminal today; the backend only records the result. We keep it that way — no money-movement logic is relocated, removing the highest-risk change from scope.
✅ The field app is protected
Legacy API paths stay live throughout, so existing SmartPOS installs keep working with no forced update.
✅ No data risk
The service uses the existing shared database — there is no data migration and no cutover of data ownership.
⚠️ Two external gates can dominate the calendar
A payment-gateway (TSYS) test account and a PCI compliance review. These are dependencies on other teams, not engineering effort, and should be started early.
⚠️ A prerequisite runs in parallel
The payments step depends on the separate destructuring/callback-modernization cleanup of the source endpoints; it's estimated separately and shouldn't be assumed inside these numbers.
